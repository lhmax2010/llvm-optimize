102: ## 2. BOLT+PGO 产品化
103: 
104: ### 2.1 候选方案
105: 
106: | 方案 | 构建内做什么 | 构建时间 | 资源 | 主要代价 |
107: |---|---|---|---|---|
108: | 甲：构建内完整 PGO | 插桩构建 → 训练 → 合并 → 带 profile 正式构建 → BOLT 插桩、训练、优化 | 新增步骤约 81 分钟（历史分项相加的规划值，不是同基线完整构建的受控增量） | 单进程峰值 VmHWM 17.0e9 B（BOLT 插桩）；磁盘已知部分规划下界约 92–96 GiB，加 30 GiB 保留线后为 122–126 GiB（59 号第 3、7 节），真实峰值未测 | 时间和磁盘最大；需要在构建内新增 merge-fdata、插桩 runtime，以及训练输入作为源文件 |
109: | 乙一：两份 profile 都预采集，离线成对生成（推荐） | 带 PGO profile 正式构建 → 用预采集的 BOLT profile 做 rewrite（流程与现状相同） | 省去构建内采集步骤；但 PGO 可能改变编译、链接、静态库转换和 BOLT 各阶段的耗时与资源，整包增量待同基线实测 | 待实测 | 两份 profile 必须与构建输入严格对应；输入一变，就要离线重新生成或重新认证 |
110: | 乙二：PGO profile 预采集，BOLT profile 在构建内采集 | 带 profile 正式构建 → 构建内 BOLT 插桩、训练、合并、优化 | 在乙一基础上再 +461 s（实测） | 单进程峰值 VmHWM 17.0e9 B；临时磁盘约 +3.8 GB（插桩 clang 0.58 GB + 原始 fdata 3.0 GB + 合并结果 0.19 GB） | 改动已通过评审的 BOLT 流程：新增两个 ninja 目标，重新认证 111+2 任务白名单，替换 profile SHA 门禁；23 份训练输入及其完整编译参数要作为源文件发布 |
111: 
112: 推荐乙一，理由如下：
113: 
114: - 它是现状的最小扩展。现在的 BOLT profile 已经是预采集、随源码发布的，乙一只是把 PGO profile 用同一套机制一起发布。
115: - BOLT 的流程、匹配公式与阈值（-stale-threshold=5，R 和 S/N 都不超过 5%）、rewrite 参数都不变。需要改的是 helper 中固定的 profile 身份：从一份改为按开关组合选择两份（第 2.2 节），并在新配置下重新确认任务闭包、工具构建和全部门禁。
116: - 体积可接受。合并后的 BOLT profile 约 194 MB，按现有 Source1200 的压缩比看，压缩后预计在 10–20 MB 量级；PGO profdata 52.5 MB，压缩后的大小待测。
117: 
118: 乙一具有可行性依据：基线是自托管构建（用快照里的上一版 clang 编译 llvm 包），63 号已证明同一提交、同一快照下，本地与 QB 的 clang 逐字节相同。但 63 号只证明了已测的非 PGO 配方在指定快照下可复现，不能直接推出 PGO 配方、或换一个构建编译器时也同样可复现。离线 profile 是否适用，由第 2.2 节的输入身份检查、实际产物身份和兼容性认证共同确认。
119: 
120: 乙二和甲都保留为备选，不作为默认方案。

122: ### 2.2 乙一的具体设计
123: 
124: **离线生成**（独立脚本，不在 RPM 构建内运行）
125: 
126: - 在与 QB 相同快照的 gbs 根里，按甲的流程一次完成以下步骤：
127:   1. 构建插桩 clang；
128:   2. PGO 训练，合并得到 llvm.profdata；
129:   3. 用这份 profdata 构建正式的 PGO clang；
130:   4. 在这个 PGO clang 上做 BOLT 插桩、训练、合并，得到 BOLT profile。
131: - 两份 profile 和一份共同清单 `llvm-profiles.manifest` 在同一次运行中产生，不能分开替换。
132: - 清单记录：
133:   - 输入身份（定义见下）；
134:   - spec 提交与 tree；
135:   - 快照名与 build.conf SHA；
136:   - 插桩参数，包括 `-mllvm -vp-counters-per-site` 的取值；
137:   - PGO 与 BOLT 两份训练清单（含 SHA 和完整编译参数）；
138:   - llvm-profdata、llvm-bolt、merge-fdata 的版本与 SHA；
139:   - 插桩运行期间 `LLVM Profile Warning` 的条数与首行原文；
140:   - 两份 profile 的 SHA 与大小（压缩前、压缩后）；
141:   - BOLT 匹配结果（N/M/S/U/Q、R、S/N）。

149:   - 现有 BOLT 的 23 份训练输入（13 份 ARM + 10 份 AArch64，其中 3 份是合成文件）只能作为初始资产，未经审计不能声称代表全平台负载。
150: 
151: **输入身份**：分为强制比对的部分和只记录的部分。清单分成两部分：一是"配方摘要"，即生成 profile 时的编译输入；二是"资产清单"，即生成出来的 profile 及其 SHA。资产本身不计入配方摘要，避免自引用。
152: 
153: 强制比对（不一致则构建失败）：
154: 
155: 1. **编译输入的内容摘要。** 在 %prep 结束、全部补丁已经应用之后，对解出的源码树求确定性摘要：按相对路径排序，计入路径、文件类型、有效 mode、符号链接目标和文件内容；不计时间戳。%prep 解出的 MLGO 模型资产在源码树内，一并计入。
156:    - 不对补丁文件本身求摘要。73 号中，0008 补丁只因提交说明折行，SHA 就从 ffe7768b… 变为 afca2209…，而代码正文逐字节相同；按补丁文件求摘要，会让每次只改提交说明、补丁重新编号或拆分的发布都失配。上游源码包和各补丁文件的 SHA 另行写入清单，作为来源记录，不作为身份判据。
157:    - 排除规则作用于展开并应用补丁之后的路径，不作用于补丁容器文件。以下内容明确排除；排除清单同时写进 spec 注释和清单，增删需要评审：
158:      - 源码树中的 `packaging/` 目录（如果源码包把它带进了源码树）；
159:      - `llvm.spec`：其中影响编译的部分，由第 2 项的实际参数和 cmake 命令行覆盖；另外 GBS 写入的 VCS 行每个提交都会变化；
160:      - `clang-bolt-helper.py`、`llvm-static-archives-native.py`：只做门禁和归档转换，不参与 clang 的编译；
161:      - PGO profile、BOLT profile 和清单本身。
162:    - 求摘要会多遍历一次源码树，耗时在实施时实测并记入第 2.4 节报备。
163: 
164:    清单记录生成 profile 时所用的配方提交；包含这些资产的发布提交，由发布记录另行绑定。
165: 2. **实际生效的固定编译与链接参数串，以及 %build 中完整的 cmake 命令行**（全部 -D 选项原样计入，不做"是否影响代码生成"的人工筛选）。两个例外：
166:    - 调度参数：`LLVM_PARALLEL_COMPILE_JOBS`、`LLVM_PARALLEL_LINK_JOBS`、ninja -j 和 ThinLTO backend 线程数，只记录、不强制。这一例外的前提，是第 4.2 节并行度调参按口径 A 的逐字节实证通过；实证不通过，就收回这一例外。
167:    - `LLVM_PROFDATA_FILE`：比较所指文件的 SHA，不比较路径。离线生成与 GBS 构建中 profile 的存放路径可能不同。
168:    - 源码树内资产的路径参数：spec 用 `$PWD` 拼出 MLGO 模型和运行时对象的路径（如 `TENSORFLOW_AOT_PATH`、`LLVM_MLGO_EMBED_TF_XLA_RUNTIME_OBJECTS` 及四个模型 header/object 参数），同一份资产放在不同构建目录时参数串就不同。对明确列出的这些参数，保存原始 argv，另外生成一份用于身份比较的表示：路径改写为相对 %prep 源码根的路径，并附所指资产的内容摘要。不得对整个参数串做路径替换，也不得规范化目标三元组、sysroot、安装路径或未列出的参数。构建根本身作为强制身份字段单独比较（第 4 项），不同构建根就是不同身份。
169: 3. **构建工具链的上游版本号。** 不按包名查询：本 spec 不产生名为 `lld` 的包，lld、ld.lld 都在 llvm 主包里（spec %files 第 735–736 行），`rpm -q lld` 在正常构建根里会因"未安装"而失败。改为按实际使用的工具检查：
170:    - 从 CMakeCache.txt 取 `CMAKE_C_COMPILER`、`CMAKE_CXX_COMPILER`、`CMAKE_AR`、`CMAKE_RANLIB`；链接器由构建编译器的 `-print-prog-name=ld.lld` 解析（对应 `LLVM_USE_LINKER=lld`）。
171:    - 每个工具解析为真实路径，执行 `rpm -qf --qf '%{NAME} %{VERSION} %{RELEASE}\n'`，并解析工具自身 `--version` 输出的上游版本号。
172:    - 任一工具不属于任何包、版本无法解析、`rpm` 的 VERSION 与工具自报版本不一致，或与认证身份的上游版本号（例如 22.1.8）不一致，就失败。包名、路径和 Release 只记录。
173:    - 检查的是绝对路径指向的实际文件，PATH 中另一个同名工具不影响结果。
174: 4. **CMake 配置结果。** cmake 完成后，对生成的配置头求内容摘要：`include/llvm/Config/config.h`、`llvm-config.h`、`abi-breaking.h`、`Targets.def`、`AsmPrinters.def`、`AsmParsers.def`、`Disassemblers.def`、`TargetMCAs.def`、`tools/clang/include/clang/Config/config.h`。
175:    - 理由：spec 没有显式设置 zlib、zstd、libxml2、terminfo、libedit、libffi 等功能开关，LLVM 会按构建根里能否找到这些开发包自动开关，clang 的代码随之改变。这些结果不出现在 cmake 命令行里，而构建根包清单只记录、不强制，前三项全部通过时这类差异会被放过。
176:    - 配置结果还包括 CMake 编译参数探测（HandleLLVMOptions 中 `check_*_compiler_flag` 的结果）以及它对最终编译命令的影响。这些结果既不在 cmake 命令行里，也不在配置头里。对 clang、lld、llvm-ar 及其依赖库的全部编译边，记录有序的 FLAGS、DEFINES、INCLUDES（CMake 探测到的宏和头文件目录在后两者里），按实际规则展开响应文件，不排序、不去重。
177:    - 用于身份比较的路径表示，沿用第 2 项的显式白名单及其认证结果，不另行采用"删除构建目录前缀"这类通用规则；宏字符串值和 prefix-map 规则不做通用路径替换。PGO 开启时，FLAGS 里的 `-fprofile-instr-use=` 按第 2 项 `LLVM_PROFDATA_FILE` 的规则改为所指文件的 SHA。原始表示和比较表示同时保存。
178:    - **构建根路径单独作为强制身份字段。** 全部编译边的 INCLUDES 都含构建根下的绝对路径（GBS 和 QB 目前都是 `/home/abuild/rpmbuild/BUILD/llvm-22.1.8`），白名单不覆盖它们，所以构建根一变，身份必然失配。构建根的原文单独记录、单独比较。
179:    - 验证用例：
180:      - 构建根相同，只把同一份已认证资产放到白名单允许的另一位置：按认证路径规则通过；
181:      - 换构建根：必须失配；
182:      - 资产内容改变、DEFINES 改变、包含目录顺序改变：必须失配；
183:      - 参数字符串中恰好含构建根前缀：不能被隐藏。
184:    - 第 2 项中"用两个不同路径的构建根做对照认证"的要求，随这一条改为：构建根不同就是不同身份，不做跨构建根的认证。
185:    - 实施前，先逐行审计这些头文件和参数摘要：找出随构建根变化、但不影响 x86_64 代码生成的字段（例如 clang 的 HOST_LINK_VERSION），列入排除规则；同时确认清单是否完整。审计结果写成固定附件，冻结之后才启用。审计未完成，乙一不上线。
186: 
187: 只记录、不强制（不一致时只在构建日志中打 warning）：
188: 
189: - 构建工具链的 Release 号与 VCS 提交号；
190: - 编译器、链接器、归档工具二进制的 SHA；
191: - 构建根完整包清单（rpm -qa 排序后）的摘要，以及其中 gcc、libstdc++、glibc 等头文件和库所在包的版本；
192: - 快照名；
193: - 上游源码包和各补丁文件的 SHA。
194: 
195: 这样分的理由：基线是自托管构建，每次 QB 重建，下一次构建都会拿到新的编译器二进制，以及新的 Release 号和 VCS（71 号中 T 的 Release 为 2.1、D 为 5.1，VCS 随每个提交变化）。如果把这些设为强制，每发布一次就必须追加认证一次。
196: 
197: 这一折中的保证范围有限，要写明：
198: - 上游版本号相同，只说明来源声明一致，不等于构建输入等价。
199: - 配置结果摘要能拦住构建根中功能开关的变化，但拦不住构建编译器或 libstdc++ 头文件本身的变化。
200: - BOLT 匹配门禁只检查 BOLT profile 的适配程度，不能替代 PGO、功能和消费者性能的认证；在"PGO 开、BOLT 关"的组合下，它完全不起作用。
201: - 快照漂移（构建编译器、libstdc++ 头文件等）会不会改变 clang 自身的代码，由下面的 T/D 归因实验给出证据。证据出来之前，这一折中只是临时安排，最终是否把工具链 Release 号或 libstdc++ 版本改为强制，由第 7 节裁决。
202: 
203: **T/D 两个身份与归因实验**：Toolchain（debug）和 Base-Dev（release）先作为两个不同的身份。同一份 BOLT profile 在 QB 上，Toolchain 的过期函数数 S=0，Base-Dev 为 S=23（71 号）。这说明两边送进 BOLT 的 clang 相对这份 profile 的匹配结果不同；它不给出两边全部代码差异的数量，也不给出原因。两边至少有三处同时不同：
204: 
205: - 调试参数：`-g2 -gdwarf-4 -g` 对无；
206: - 构建编译器：快照中的 clang 22.1.8-2.1 对 22.1.8-5.1；
207: - GCC/libstdc++：14.2.0-1.7 对 14.2.0-1.24。clang 自身大量模板是经 libstdc++ 头文件实例化的。
208: 
209: 本包用 ThinLTO 构建。单独编译一个源文件只能得到 bitcode；去掉 -flto 得到的机器码又与最终链接不同。最终机器码是 lld 的 ThinLTO 后端在跨模块导入和内联之后生成的。所以逐源文件编译、比较 `.text` 的做法，即使得到"字节相同"，也可能只是没有复现 ThinLTO 链接，会把原因错归到快照。

243: PGO 生效检查按开关执行：PGO 开启时，检查预期作用范围内的目标在 build.ninja 中确实带 `-fprofile-instr-use=`，并且路径指向认证映射指定的那个文件（核对 SHA）；PGO 关闭时，检查这些目标没有意外带上 profile-use 参数，也不要求提供 PGO 资产。BOLT 的资产检查按组合单独执行，两者互不影响。

247: **spec 中的使用**
248: 
249: - 新增 Source：PGO profile、与之成对的 BOLT profile、清单。现有的 Source1200（非 PGO 用 BOLT profile）继续保留。
250: - 当前输入身份必须出现在清单的认证列表中，否则构建失败。清单可以记录多个已认证的身份。
251: - 通过 LLVM 自带的 CMake 选项 LLVM_PROFDATA_FILE 传入 PGO profile。上游 CMake 在文件不存在时只打 warning，所以 spec 在 cmake 之前自己检查文件存在，cmake 之后检查 build.ninja（见上文"检查时机"）。
252: - **PGO 匹配程度**：
253:   - 先确认 profile 的类型：Frontend、IR 还是 CSIR，并核对对应的使用阶段。LLVM 的插桩构建默认生成 IR profile，匹配在 IR PGO pass 中进行；前端的 -Wprofile-instr-out-of-date 汇总诊断不适用于 IR profile，而 IR 侧的缺失与 COMDAT/weak 不匹配警告默认被抑制（llvm-22.1.8 的 CodeGenModule.cpp 第 857–872 行、PGOInstrumentation.cpp 第 1407–1439 行）。
254:   - 只有取得同一统计域内完整的 matched、missing、mismatched 计数，才计算匹配率，并写明统计单位（函数实例还是去重函数），以及 COMDAT、重复编译单元和 ThinLTO 阶段如何处理。
255:   - 不得用警告条数或 profdata 记录数代替当前构建的分母。取不到完整计数时，记为 UNKNOWN；不把"没有警告"解释为"零过期"，也不据此追加认证身份。
256:   - 辅助指标：本包用 ThinLTO，IR PGO 的注解在预链接阶段完成，构建树中 clang 各编译单元的 .o 就是带注解的 bitcode。对这些 bitcode 执行 `llvm-dis`，统计已定义函数中带 `function_entry_count` 元数据的比例，称为"最终 IR 注解覆盖率"，不得称为 PGO 匹配率：最终预链接 bitcode 中的函数集合不一定就是 profile-use 当时的候选集合（之后还有删除、克隆和内联），不同编译单元的同名局部函数也不是同一个函数，同名 ODR 定义也可能有不同的 CFG/profile hash。
257:   - 完整的匹配计数，优先在 profile-use 查询发生的阶段取得：记录模块身份、函数/profile key、函数 hash 和 matched/missing/mismatched 状态。局部函数按模块区分；COMDAT/ODR 去重必须保留 hash 不同的定义。统计范围覆盖实际链接进 clang 的 LLVM/Clang 编译单元。取得手段尚未确定：`-pgo-warn-*` 只报缺失和不匹配，给不出分母；`-mllvm -stats` 需要启用了统计的编译器，快照里的编译器是否支持未知；转换器会拒绝 `-mllvm`。候选做法是用 pass 插件或打了补丁的 `opt`，对 profile-use 之前的 IR 重放 profile 查询。手段确定并通过夹具验证之前，匹配率记为 UNKNOWN。
258:   - 离线重放的结果要算作当前构建的计数，还需证明重放与真实的 profile-use 阶段等价：
259:     - 输入恰好是实际 profile-use 阶段的输入 IR；
260:     - 目标配置、profile 类型、查询选项以及 key/hash 的生成规则都相同；
261:     - 至少取若干真实编译单元，把重放结果与实际 profile-use 阶段逐函数核对 key、hash 和查询状态；
262:     - 用于观测的改动不得改变原有的优化流程和输出。
263:     合成夹具通过只证明计数逻辑正确，不能单独证明这一点。无法证明时继续记为 UNKNOWN。CSIR 部分单独认证。
264:   - 如果 profile 是 CSIR，上下文敏感的那部分在 ThinLTO 后链接阶段才使用，预链接 bitcode 的统计覆盖不到，要单独说明。
265:   - 需要额外诊断选项（如 `-mllvm -pgo-warn-missing-function`）时，只在离线认证构建中使用。这类选项会进入静态库成员的记录命令，而转换器会拒绝 `-mllvm`，所以认证构建要关闭转换，或另行处理。
266:   - llvm-profdata 统计的有 profile 函数数与计数占比，作为辅助记录，和上一个已认证基线比较，不作分母。
