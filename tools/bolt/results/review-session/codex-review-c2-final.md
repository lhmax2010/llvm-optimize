## 5. Correctness of the PM attribution

The comparison is between locally built C2 B1 and QB 1232863 at 361395 PS5. Three things vary across those endpoints: the PS4 parent's default-linker settings, 361624's pre-existing PS4 changes including build IDs, and the corrective delta to PS4. There is also a recorded RPM release/debug-prefix difference. The source comparison tells us which changes reach which targets. The two builds alone cannot isolate each possible cause.

**128 ELFs with changed RELRO padding — accept the padding explanation, qualify the whole-file explanation.** I checked the retained old and new program headers against all 128 padding records. On every side the section is SHT_NOBITS, ends on a 4 KiB boundary and ends exactly at the end of PT_GNU_RELRO. The endpoint is unchanged in 125 pairs, moves down one page in two and up one in one. The PT_LOAD flag sequences agree pairwise. This matches lld/ELF/SyntheticSections.cpp:2778 and LinkerScript.cpp:1285–1288. The linker's alignment rule explains the padding following a changed layout.

All 128 also gained a build-ID note. For 14 of them the .text bytes changed, for four .rodata changed, and smaller subsets have .init, .plt or unwind-section differences. Task146's rpm_v2.py skips the instruction comparison as soon as a section prerequisite fails. All 128 records explicitly report that skip. lld and llvm-exegesis, whose disassemblies passed, are separate records.

I independently found the parent's linker literal in two of those 14 changed text sections. At section-relative offset 0x216fc92 in libclang-cpp.so.22.1 and 0x8e84a2 in libclang.so.22.1.8, the new initialization writes the immediate bytes for `lld\0` and length 3. The corresponding old instructions store the empty value and zero length. This is a real, expected behavior change inherited from the parent. The other 12 .text pairs also have equal old/new section lengths, which alone cannot establish operand or instruction equivalence. The main x86_64 spec delta adds no compilation flag for these images. They are installed before the in-tree BOLT work, and the pipeline checks the ordinary install against its snapshot. I found no source path by which the C2 fixes rewrite them. A claim that *every byte difference* has been attributed would still require resolving the remaining changed code/data references, including their destination values. The evidence supports accepting these files for upload with that distinction recorded.

**LLVMgold.so and ompdModule.so — confirmed at whole-file byte level.** Both are CMake MODULE targets (llvm/tools/gold/CMakeLists.txt:15 and openmp/libompd/gdb-plugin/CMakeLists.txt:27). Neither pair has a build ID. PS4's EXE and SHARED flag assignments leave the module linker flags alone. I compared each pair of installed files and independently computed the CRC32 of each corresponding old and new debug file. Exactly the four CRC bytes changed in each entire module. LLVMgold.so changed from 37ca18c3 to e21b4258, and ompdModule.so from b6c05b1f to 8a4b9ab7. This accounts for every changed byte in both shipped modules.

**clang-22 — the constructor layout explanation is supported.** Task146 counted 146,957 equal normalized function keys of 146,959. C1 and C2 in the two remaining mangled names are constructor aliases covering the same implementation on each side. The earlier native Driver.cpp.o comparison independently locates the empty-to-lld initialization in input to the packaging workflow. The old shipped constructor has 427 hot and 310 cold instructions. The new one has 732 in one range.

I also checked the recorded constructor differences against the retained symbolized ELF copies. I used the numeric direct-branch targets from llvm-objdump, followed unconditional jumps and paired each inverted conditional with its ordered true/false successors. I compared the remaining symbolic instructions with register and memory displacements retained. I allowed the two initialization stores and resolved the differently named .L.str.4/.L.str.5 reference to the same NUL-terminated bytes, `/emul`, in both load images. This left 707 instruction nodes per side. Every node paired uniquely, the entry points paired, and I verified the mapped ordered direct successors of every node. This independently accounts for the branch inversions and block movement in clang-v2-raw-differences.txt. It checks decoded instructions and ordinary direct control flow. Unwind metadata, indirect target resolution and whole-program equivalence are outside that check.

The 146,957 figure should retain the word *normalized*. The comparison masks register displacements, local labels and certain symbol annotations, and considers sized function ranges. Equal keys establish equality under that comparison. I found no indication of a C2 rewrite regression. A controlled comparison on identical rewrite inputs would be needed to make a stronger claim about exclusive causation. For the two modules the binary comparison is conclusive, and for the constructor the direct-flow comparison substantially narrows that uncertainty.

## 6. Commit message and wording

The message accurately states the intended host architectures, provider checks, per-architecture registration gate, runtime flag scope and single merge-fdata install. “Build ... on x86_64 and aarch64” describes the spec's supported hosts. The validation report should continue to identify B2's actual host as x86_64.

One wording nit: “enable its declarations” is imprecise. The guard at bolt/lib/Target/X86/X86BoltMnemonicTables.cpp:27 encloses **definitions** of X86 helpers and generated tables. “Compile the X86 mirror only in standalone dylib builds” would cover both the source-list condition and private compile definition. The source comment at lines 9–14 also says static archives are unavailable, although this spec installs llvm-static-devel to satisfy CMake export validation. The relevant fact is that the standalone tools link the dylib and need definitions it does not export. Both wording items can follow the planned sign-off-only upload.

For the validation record I would use: “B1 and B2 passed on x86_64. PM accepted the 131 remaining v2 exceptions. All 128 padding sections end at the RELRO page boundary. Some files also contain other section changes, including the parent default-LLD initialization in both Clang DSOs. Both module changes are confined to valid debuglink CRCs. The two differing clang function keys alias one constructor whose direct control flow matches after accounting for linker initialization and block layout.”
