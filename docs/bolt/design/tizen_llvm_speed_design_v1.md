# Tizen x86_64 LLVM：BOLT+PGO 产品化、构建资源优化与其他提速方案 设计 v1

日期：2026-11-06
范围：Tizen-Base-Toolchain 与 Tizen-Base-Dev 中 x86_64 的 llvm 包。qemu-accel 从这个包取出 clang、lld、llvm-ar，用于交叉编译 armv7l/aarch64 包，所以这个包的执行速度直接决定平台包的编译速度。
基线：sandbox/lhmax2025/bolt_pgo = 9e39fa8a（hybrid d4d6ca16 → BOLT+debuglink f2553114 → 固定编译参数+release 转换 9e39fa8a）。这三个提交正在改接到总部 Change 359934（当前 patch set 10）上，改接结果另见 69 号文档。

## 0. 目标与验收口径

本月四项目标：

1. 交付完整的 BOLT+PGO 实现，并给出编译速度提升数据。
2. 在不影响效果的前提下，降低编译 LLVM 本身所需的内存、磁盘和时长。
3. 代码上传前，必须经三家外部评审确认没有问题。
4. 在静态链接、-O3、BOLT/PGO 之外，评估其他提速方案。

硬约束（沿用既有裁决）：

- 不能导致其他包编译失败。
- 不能让其他包的运行时性能下降，也不能让它们的运行内存升高。
- LLVM 包自身编译时，内存若显著增大，必须先报备，在 QB 上验证后才能推进。
- 本地工作机只做功能和稳定性验证，不作为性能结论的来源。性能结论以 QB 为准，按内部的 A/A + A/B 交错协议判定。
- 本地验证必须与 QB 条件一致：同一快照、同一 build.conf、同一仓库。

"效果不变"的定义（构建资源优化部分适用，第 4 节）：

- 所有已安装 RPM payload 中的文件内容，与同提交、同快照的基线逐字节相同。允许的例外沿用已确认规则：
  - 记录节：.GCC.command.line、.llvmcmd、.comment；
  - debuglink CRC；
  - release 号带来的 .debug 两类差异（67 号第 8 节）。
- RPM 文件本身的字节（压缩方式、头部时间戳）不属于"效果"。但凡是改动 RPM 压缩方式的方案，都单独列为待裁决项，不默认纳入。
- 调试信息格式的改变（压缩调试节、split DWARF、DWARF 版本）属于效果改变，不在本设计范围内。

## 2. BOLT+PGO 产品化

### 2.1 候选方案

| 方案 | 构建内做什么 | 估计增加的构建时间 | 内存 | 磁盘 | 可复现性 |
|---|---|---|---|---|---|
| 甲：构建内完整 PGO | 插桩构建 → 训练 → 合并 → 用 profile 正式构建 → BOLT | 约 +80 分钟（≈ +45%） | 约 20 GiB | 85–95 GiB | 只依赖源码，完全可复现 |
| 乙：预采集 PGO profile 随源码发布，BOLT profile 在构建内采集 | 用 profile 正式构建 → BOLT 插桩、训练、优化（与现在相同） | 仅为"带 profile 编译"的额外开销，待实测 | 约 20.2 GiB（按 59 号的 21.7e9 B） | 接近现状 63 GiB，待实测 | 依赖随包发布的 profile 文件 |
| 丙：两份 profile 都预采集 | 用 profile 正式构建 → 用预采集的 BOLT profile 优化 | 最少 | 同乙 | 同乙 | BOLT profile 绑定具体二进制，源码或参数一变就过期（已实测 85.3%），并且 fdata 有 3.0 GB |

丙不可行：BOLT profile 与二进制强绑定，体积也太大。

推荐乙，同时在 spec 里保留甲作为可开关的备选（默认关闭），用于 profile 再生成和对照。理由：

- 乙基本不增加构建时间。
- 现有 BOLT 流程不用改。
- PGO 的大部分收益来自中端优化（内联、布局），对 profile 小幅过期并不敏感。版本升级时重新生成即可。

### 2.2 乙的具体设计

profile 的生成（离线工具，不在 RPM 构建内运行）：

- 新增离线脚本，按甲的流程生成 llvm.profdata。脚本记录以下内容，写进 profile 的伴随清单：
  - LLVM 源码提交；
  - spec 提交；
  - 插桩构建所用的快照和参数；
  - 训练输入清单（含 SHA）；
  - llvm-profdata 版本。
- 训练集要求：
  - 覆盖 armv7l 和 aarch64 两个目标，可附加 x86_64；
  - C 和 C++ 都要有，取自真实 Tizen 包的预处理输入；
  - 与第 3 节的测速集严格不相交。
- 产物：llvm.profdata（约 52.5 MB），以及伴随清单 llvm.profdata.manifest。压缩后大小待实测。

spec 中的使用：

- 新增 Source：profile 文件及其清单。%prep 校验 profile 的 SHA 与清单一致，不一致则构建失败。
- 通过 LLVM 自带的 CMake 选项 LLVM_PROFDATA_FILE 传入 profile，不手写 -fprofile-instr-use。
- 只作用于最终编译阶段。若存在自举的第一阶段，第一阶段不使用 profile。
- 过期监测：
  - 收集编译期间 clang 给出的 profile 过期 / 未覆盖警告（-Wprofile-instr-out-of-date、-Wprofile-instr-unprofiled），在构建日志末尾汇总为一行：总函数数、不匹配数、比例。
  - 按现有"项目参数变化只打 warning、不中断构建"的原则，过期比例超过阈值时只打 warning，不让构建失败。阈值初定 10%，待裁决。
- 开关：%bcond pgo，默认开启。关闭时行为与 9e39fa8a 完全相同。

BOLT 部分：

- 沿用 f2553114 的构建内插桩、训练、优化流程，在 PGO 版 clang 上重新采集 profile。
- 训练输入沿用现有的 23 个文件（13 ARM + 10 AArch64）。

-use-old-text 放不下时的处理（待裁决，三选一）：

- 选项一：允许 BOLT 自动改用新段（现状行为）。日志打印"需要 / 可用"两个数，体积增量写进构建日志。
- 选项二：先尝试 -split-functions / -split-all-cold，缩小热代码，力争能放进旧段。需要实测效果和体积。
- 选项三：放不下就让构建失败。

推荐选项一加打印，同时安排选项二的实测。

### 2.3 范围扩展（第二阶段）

- lld、llvm-ar 用同一套机制（PGO profile 一并覆盖，BOLT 各自采集）。
- 前提：QB 全平台日志显示链接和归档占比足够大。这仍是待定项，等 QB 日志出来再定。
- 本月只为 clang 交付；lld、llvm-ar 只做可行性和资源数据。

### 2.4 资源报备

- 乙方案下，正式编译阶段的内存约 20.2 GiB，比现状多约 3 GiB。按硬约束，需要先报备并在 QB 上验证。
- 磁盘和时长待实测（第 6 节第一批次）。
- 周报只列实测的时长、内存和磁盘。

### 2.5 正确性验收

- 功能：
  - 本地 T/D 两个配置完整构建；
  - install/LLDB 21 项检查；
  - 在固定、与训练集不相交的 90 份 TU 输入上，四个版本的 clang（无 BOLT、仅 BOLT、仅 PGO、PGO+BOLT）生成的 .o 逐字节相同。PGO 和 BOLT 只改变编译器自身的代码，不应改变编译器的输出。
- QB：Tizen-Base-Toolchain 与 Tizen-Base-Dev 两个项目全部架构通过。

## 3. 测速方法

### 3.1 本地（只给方向，不作结论）

- 测速集：90 份 TU 输入（已按 SHA 恢复，armv7l/aarch64/x86_64 各 30 份），与 BOLT/PGO 训练集不相交。若有重叠，从测速集中剔除并列出。
- 版本：
  - V0：tizen_base 当前 HEAD 的 GCC 编译版（f999bd40 的 QB 产物，代表总部目前的状态）；
  - V1：hybrid（无 BOLT）；
  - V2：仅 BOLT（9e39fa8a）；
  - V3：仅 PGO；
  - V4：PGO+BOLT。
- 执行：
  - 版本之间轮换交错（V0 V1 … V4，再从 V0 开始），每个版本至少 5 轮；
  - 每份 TU 在固定 CPU 上串行编译，用 /usr/bin/time -v 记录 user+sys、wall 和最大 RSS；
  - 每轮开始前记录 load average，超过 1 时等待，最多 10 分钟，仍然超过就把该轮标记为"有干扰"。
- 报告：
  - 以 user+sys 为主指标，wall 为辅；
  - 给出每个版本相对 V2 的中位数比值和 bootstrap 95% 置信区间；
  - 同时列出最大 RSS 的变化（硬约束：编译器内存不能升高）。
- 包体积：列出各版本 clang 二进制和 llvm 主包的安装大小。

### 3.2 QB（结论来源）

- 按内部 A/A + A/B 交错协议执行，判定口径不在本设计内定义。
- 本设计只提供可直接提交 QB 的分支和每个版本的产物 SHA。
- 首选负载：Chromium（使用平台 clang）。另取若干 C/C++ 为主的 Base 包作为补充。

## 4. 降低 LLVM 自身构建的内存、磁盘和时长

### 4.1 第一步：先测清楚时间、内存和磁盘花在哪里（不重新构建）

用 63 号已有的本地 T 构建日志和 cgroup 采样，以及 QB 1216409/1216410 的日志，按阶段拆分：

- cmake；
- 自举第一阶段（如果有）；
- 编译；
- ThinLTO 大链接（clang、libLLVM.so、libclang-cpp.so、lld、liblldb）；
- install；
- 静态库转换；
- BOLT 三步；
- find-debuginfo / debugedit；
- RPM 打包压缩。

每个阶段给出：

- 时长；
- 该阶段的内存峰值，以及峰值时的进程；
- 该阶段结束时构建根的占用，以及磁盘峰值出现的时刻和主要目录。

后续候选按实测收益排序，不靠估计。

### 4.2 候选项

| 编号 | 方案 | 针对 | 是否改变产物 | 验证方式 |
|---|---|---|---|---|
| 资源一 | 静态库转换提速：核对当前并发度，以及每个成员的转换是否重复执行了中端优化；改为按核数并行（受内存上限约束），重复成员只转换一次 | 时长（QB 上 66 分钟） | 不应改变；输出须与现转换器逐字节相同 | 7706 个成员的转换输出逐字节比较 |

| 资源三 | 自举第一阶段瘦身（如果有）：第一阶段只构建用于编第二阶段的工具，目标架构只保留 X86，不带调试信息 | 时长、磁盘 | 理论上不改变最终产物，须实证 | 最终 RPM payload 逐字节比较 |

| 资源五 | 重链接单独限流：对 clang、libLLVM.so、lld、liblldb 等大 ThinLTO 链接使用单独的 ninja job pool，小链接保持现有并发 | 内存峰值，时长基本不变 | 不应改变（ThinLTO 输出与线程数无关，须实证） | 内存峰值对比，RPM payload 逐字节比较 |

## 5. 其他提速方案评估

评估顺序按"预期收益 / 风险"排列。每项都先在本地做功能和方向验证（第 3.1 节的方法），有正向信号才进 QB。

| 方案 | 原理 | 预期 | 主要风险 / 前提 | 本月目标 |
|---|---|---|---|---|
| 替换 clang/lld 的内存分配器（静态链入 mimalloc 等） | clang 大量小对象分配，glibc malloc 在多线程和碎片化场景下开销较大 | 待实测 | 新增 Base 依赖包及其许可；编译器峰值内存可能升高，需要报备 | 本地原型：90 TU 的时间和 RSS |
| 代码段使用大页（BOLT -hugify，或 2 MB 对齐加 THP） | clang 代码段上百 MB，iTLB 缺失明显 | 待实测 | 依赖 QB 构建机内核的 THP 设置（未知）；不可用时必须自动退回、不能报错 | 本地原型和退回路径验证 |
| 静态 clang 的全程序去虚拟化（-fwhole-program-vtables 配合可见性控制） | clang 的 AST、Sema 中虚调用多 | 待实测 | 可能破坏 clang 插件接口；正确性风险较高 | 只做可行性调研，不进本月交付 |
| perf 采样驱动的优化（AutoFDO / Propeller） | 用真实负载上的采样 profile，免去插桩构建 | 与 PGO 同量级 | 需要硬件 LBR 和 perf；QB 上无法采集 | 只做可行性调研，列入后续计划 |
| -fno-plt、-Bsymbolic 等动态链接优化 | 减少 PLT 和符号插桩开销 | clang、lld 已是静态链接，收益很小 | — | 不做，记录理由 |
| 提高 -march 等级 | 使用更新的指令集 | 有收益 | QB 构建机 CPU 未知，可能出现 SIGILL；与"沿用项目 -march"的裁决冲突 | 不做，记录理由 |
| 平台包默认使用 lld | 缩短包的链接时间 | 有收益 | 在单独的工作线中跟进 | 不在本设计内 |

## 7. 需要裁决的事项

1. PGO profile 的交付方式：推荐"预采集文件随源码发布"（乙），"构建内完整训练"（甲）只作为默认关闭的开关。
2. profile 过期超过阈值时：推荐只打 warning，阈值初定 10%。
3. PGO+BOLT 下 -use-old-text 放不下时：推荐允许自动改用新段并打印数据，同时实测函数拆分的效果。
4. "效果不变"按第 0 节的定义执行；RPM 压缩方式的改动需要另行批准。
5. 乙方案的编译内存约 +3 GiB，按规定先报备、在 QB 上验证。
6. 分配器方案若有收益，能否接受新增一个 Base 依赖包。

## 8. 风险

- 52.5 MB 的二进制 profile 放进源码包，总部可能有顾虑。备选是甲方案，代价是构建时间约 +45%。
- PGO 带来的速度收益目前只有噪声很大的本地数据，可能比预期小。最终以 QB 数据为准。
- 自举第一阶段瘦身、ThinLTO 并发调整，理论上不改变产物，但必须逐字节实证。实证不通过就放弃该项。
- QB 构建机的内存和磁盘上限未知。每项改动都只报实测值，不作"可以接受"的判断。
