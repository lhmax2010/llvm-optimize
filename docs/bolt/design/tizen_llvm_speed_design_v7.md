## 0. 目标、约束与验收口径

### 0.1 本月四项目标

1. 交付完整的 BOLT+PGO 实现，并给出编译速度提升数据。
2. 在不影响效果的前提下，降低编译 LLVM 本身所需的内存、磁盘和时长。
3. 代码上传前，必须经三家外部评审确认没有问题。外部评审是必经流程，但不能代替第 6 节的运行验证门槛。
4. 在静态链接、-O3、BOLT/PGO 之外，评估其他提速方案。

### 0.2 硬约束

沿用既有裁决：

- 不能导致其他包编译失败。
- 本地工作机只做功能和稳定性验证，不作为性能结论的来源。性能结论以 QB 为准，按内部的 A/A + A/B 交错协议判定。
- 本地验证必须与 QB 条件一致：同一快照、同一 build.conf、同一仓库。
- armv7l/aarch64 的构建行为和二进制产物不变。唯一的已裁决例外（第 7 节第 15 条）：混合链接提交修改的 CMake 模块会被安装到所有架构的开发包中，由此产生的文本变化作为行为不变的已知例外接受，并以 ARM 逐包比较证明差异只有这些模块文件。对外表述为"ARM 构建行为不变，开发包中的 CMake 模块文本有变化"，不说成"ARM 完全不变"。

内存分三类，分别报告、分别裁决，不混用，也不用一类的改善去抵消另一类的回归：

| 类别 | 指什么 | 规则 |
|---|---|---|
| 第一类 | 构建 llvm 包本身的资源 | 显著增加时，必须在试验前报备；本地先行验证，推广前在 QB 上验证 |
| 第二类 | 用安装后的 clang/lld 编译其他包时的资源 | 可接受的变化幅度待裁决（第 7 节） |
| 第三类 | 其他包产物在运行时的性能与内存 | 不得回归（硬约束） |

### 0.3 "效果不变"的两套口径

按比较对象分两套口径，比较器把口径作为必填参数，没有默认值。

**口径 A：受控的本地 A/B 比较。** 第 4 节中字节保持类候选的验证使用这一套。

- 快照、Release、工具和所有非实验变量保持一致。源码、spec、CMake 或并发参数之间，只允许出现事先登记的候选差异；比较器保存这份差异清单，发现未登记的变量变化就拒绝比较。
- 已安装 RPM payload 的以下各项与基线完全相同：文件集合、路径、类型、mode/uid/gid、符号链接目标、硬链接关系、文件内容；自动生成的 Provides/Requires；RPM 脚本。
- 允许的例外只有两类：
  - 记录节：.GCC.command.line、.llvmcmd、.comment。差异必须单列，并归因到本次登记的参数或路径变化，不能当作任意差异的豁免。
  - 归档成员头的日期字段：沿用 37 号第 10.1 节已裁决的三个条件，即成员名单与顺序一致、逐成员内容 SHA 一致、屏蔽日期字段后全字节一致。
- 默认不允许 debuglink CRC、DWARF 内容或布局的差异。一旦出现，先归因、判为未通过，不预设原因，也不自动套用口径 B 的例外。
- 口径 A 只适用于"字节保持"类候选，即并行度、调度、经认证的中间产物清理等。相同代码折叠、分配器、大页、PGO 这类会改变编译器产物的优化，不能要求编译器自身字节不变，按第 2.5 节的身份一致性、功能、安全、性能和资源协议验收。

**口径 B：本地对 QB。** 第 2.5 节的身份核对、第 3 节的版本身份使用这一套。

- 包含口径 A 的全部要求。
- 另加 67 号第 8.1 节已裁决并启用的三条规则：.debug_line 逐单元长度增量、DW_AT_comp_dir 等长加 POSIX 词法等价、debuglink CRC（先验证配对的符号文件，再验证文件名、实际 CRC 和其余 ELF 内容）。
- 按这一套，23 个包中 21 个 PASS。llvm 源码包和 debugsource 包的剩余差异如何处理，是第 7 节的裁决项；裁决前继续判 FAIL。

两套口径都不覆盖 RPM 文件本身的字节（压缩方式、头部时间戳）。凡是改动 RPM 压缩方式的方案，都单列为裁决项，默认不做。调试信息格式的改变（压缩调试节、split DWARF、DWARF 版本）属于效果改变，不在本设计范围内。

## 2. BOLT+PGO 产品化

### 2.1 候选方案

| 方案 | 构建内做什么 | 构建时间 | 资源 | 主要代价 |
|---|---|---|---|---|
| 甲：构建内完整 PGO | 插桩构建 → 训练 → 合并 → 带 profile 正式构建 → BOLT 插桩、训练、优化 | 新增步骤约 81 分钟（历史分项相加的规划值，不是同基线完整构建的受控增量） | 单进程峰值 VmHWM 17.0e9 B（BOLT 插桩）；磁盘已知部分规划下界约 92–96 GiB，加 30 GiB 保留线后为 122–126 GiB（59 号第 3、7 节），真实峰值未测 | 时间和磁盘最大；需要在构建内新增 merge-fdata、插桩 runtime，以及训练输入作为源文件 |
| 乙一：两份 profile 都预采集，离线成对生成（推荐） | 带 PGO profile 正式构建 → 用预采集的 BOLT profile 做 rewrite（流程与现状相同） | 省去构建内采集步骤；但 PGO 可能改变编译、链接、静态库转换和 BOLT 各阶段的耗时与资源，整包增量待同基线实测 | 待实测 | 两份 profile 必须与构建输入严格对应；输入一变，就要离线重新生成或重新认证 |
| 乙二：PGO profile 预采集，BOLT profile 在构建内采集 | 带 profile 正式构建 → 构建内 BOLT 插桩、训练、合并、优化 | 在乙一基础上再 +461 s（实测） | 单进程峰值 VmHWM 17.0e9 B；临时磁盘约 +3.8 GB（插桩 clang 0.58 GB + 原始 fdata 3.0 GB + 合并结果 0.19 GB） | 改动已通过评审的 BOLT 流程：新增两个 ninja 目标，重新认证 111+2 任务白名单，替换 profile SHA 门禁；23 份训练输入及其完整编译参数要作为源文件发布 |

推荐乙一，理由如下：

- 它是现状的最小扩展。现在的 BOLT profile 已经是预采集、随源码发布的，乙一只是把 PGO profile 用同一套机制一起发布。
- BOLT 的流程、匹配公式与阈值（-stale-threshold=5，R 和 S/N 都不超过 5%）、rewrite 参数都不变。需要改的是 helper 中固定的 profile 身份：从一份改为按开关组合选择两份（第 2.2 节），并在新配置下重新确认任务闭包、工具构建和全部门禁。
- 体积可接受。合并后的 BOLT profile 约 194 MB，按现有 Source1200 的压缩比看，压缩后预计在 10–20 MB 量级；PGO profdata 52.5 MB，压缩后的大小待测。

乙一具有可行性依据：基线是自托管构建（用快照里的上一版 clang 编译 llvm 包），63 号已证明同一提交、同一快照下，本地与 QB 的 clang 逐字节相同。但 63 号只证明了已测的非 PGO 配方在指定快照下可复现，不能直接推出 PGO 配方、或换一个构建编译器时也同样可复现。离线 profile 是否适用，由第 2.2 节的输入身份检查、实际产物身份和兼容性认证共同确认。

乙二和甲都保留为备选，不作为默认方案。

### 2.2 乙一的具体设计

**离线生成**（独立脚本，不在 RPM 构建内运行）

- 在与 QB 相同快照的 gbs 根里，按甲的流程一次完成以下步骤：
  1. 构建插桩 clang；
  2. PGO 训练，合并得到 llvm.profdata；
  3. 用这份 profdata 构建正式的 PGO clang；
  4. 在这个 PGO clang 上做 BOLT 插桩、训练、合并，得到 BOLT profile。
- 两份 profile 和一份共同清单 `llvm-profiles.manifest` 在同一次运行中产生，不能分开替换。
- 清单记录：
  - 输入身份（定义见下）；
  - spec 提交与 tree；
  - 快照名与 build.conf SHA；
  - 插桩参数，包括 `-mllvm -vp-counters-per-site` 的取值；
  - PGO 与 BOLT 两份训练清单（含 SHA 和完整编译参数）；
  - llvm-profdata、llvm-bolt、merge-fdata 的版本与 SHA；
  - 插桩运行期间 `LLVM Profile Warning` 的条数与首行原文；
  - 两份 profile 的 SHA 与大小（压缩前、压缩后）；
  - BOLT 匹配结果（N/M/S/U/Q、R、S/N）。
- 计数器耗尽：58 号的 830 条"静态计数器耗尽"警告，来自插桩构建过程中执行的工具，训练阶段的日志里没有。先把警告归属到具体的可执行文件和 profraw，确认这些数据是否进入了发布用的 profdata，再决定是否加大 `-vp-counters-per-site` 重新生成。确认之前，发布 profile 在这方面的完整性记为 UNKNOWN。
- 训练集要求：
  - 在采集前冻结；
  - 覆盖 armv7l 与 aarch64，并评估 x86_64 是否需要覆盖；
  - C 和 C++ 都有，取自真实 Tizen 包；
  - 列出目标、语言、优化等级的覆盖矩阵；
  - 与第 3 节的测速集按源文件隔离，不只按内容 SHA 隔离（第 3.1 节）。
  - 现有 BOLT 的 23 份训练输入（13 份 ARM + 10 份 AArch64，其中 3 份是合成文件）只能作为初始资产，未经审计不能声称代表全平台负载。

**输入身份**：分为强制比对的部分和只记录的部分。清单分成两部分：一是"配方摘要"，即生成 profile 时的编译输入；二是"资产清单"，即生成出来的 profile 及其 SHA。资产本身不计入配方摘要，避免自引用。

强制比对（不一致则构建失败）：

1. **编译输入的内容摘要。** 在 %prep 结束、全部补丁已经应用之后，对解出的源码树求确定性摘要：按相对路径排序，计入路径、文件类型、有效 mode、符号链接目标和文件内容；不计时间戳。%prep 解出的 MLGO 模型资产在源码树内，一并计入。
   - 不对补丁文件本身求摘要。73 号中，0008 补丁只因提交说明折行，SHA 就从 ffe7768b… 变为 afca2209…，而代码正文逐字节相同；按补丁文件求摘要，会让每次只改提交说明、补丁重新编号或拆分的发布都失配。上游源码包和各补丁文件的 SHA 另行写入清单，作为来源记录，不作为身份判据。
   - 排除规则作用于展开并应用补丁之后的路径，不作用于补丁容器文件。以下内容明确排除；排除清单同时写进 spec 注释和清单，增删需要评审：
     - 源码树中的 `packaging/` 目录（如果源码包把它带进了源码树）；
     - `llvm.spec`：其中影响编译的部分，由第 2 项的实际参数和 cmake 命令行覆盖；另外 GBS 写入的 VCS 行每个提交都会变化；
     - `clang-bolt-helper.py`、`llvm-static-archives-native.py`：只做门禁和归档转换，不参与 clang 的编译；
     - PGO profile、BOLT profile 和清单本身。
   - 求摘要会多遍历一次源码树，耗时在实施时实测并记入第 2.4 节报备。

   清单记录生成 profile 时所用的配方提交；包含这些资产的发布提交，由发布记录另行绑定。
2. **实际生效的固定编译与链接参数串，以及 %build 中完整的 cmake 命令行**（全部 -D 选项原样计入，不做"是否影响代码生成"的人工筛选）。两个例外：
   - 调度参数：`LLVM_PARALLEL_COMPILE_JOBS`、`LLVM_PARALLEL_LINK_JOBS`、ninja -j 和 ThinLTO backend 线程数，只记录、不强制。这一例外的前提，是第 4.2 节并行度调参按口径 A 的逐字节实证通过；实证不通过，就收回这一例外。
   - `LLVM_PROFDATA_FILE`：比较所指文件的 SHA，不比较路径。离线生成与 GBS 构建中 profile 的存放路径可能不同。
   - 源码树内资产的路径参数：spec 用 `$PWD` 拼出 MLGO 模型和运行时对象的路径（如 `TENSORFLOW_AOT_PATH`、`LLVM_MLGO_EMBED_TF_XLA_RUNTIME_OBJECTS` 及四个模型 header/object 参数），同一份资产放在不同构建目录时参数串就不同。对明确列出的这些参数，保存原始 argv，另外生成一份用于身份比较的表示：路径改写为相对 %prep 源码根的路径，并附所指资产的内容摘要。不得对整个参数串做路径替换，也不得规范化目标三元组、sysroot、安装路径或未列出的参数。启用前，先用两个不同路径的构建根做对照认证（路径可能进入记录节或调试信息）；认证不通过，就继续按原样比较、把不同构建根当作不同身份。
3. **构建工具链的上游版本号。** 不按包名查询：本 spec 不产生名为 `lld` 的包，lld、ld.lld 都在 llvm 主包里（spec %files 第 735–736 行），`rpm -q lld` 在正常构建根里会因"未安装"而失败。改为按实际使用的工具检查：
   - 从 CMakeCache.txt 取 `CMAKE_C_COMPILER`、`CMAKE_CXX_COMPILER`、`CMAKE_AR`、`CMAKE_RANLIB`；链接器由构建编译器的 `-print-prog-name=ld.lld` 解析（对应 `LLVM_USE_LINKER=lld`）。
   - 每个工具解析为真实路径，执行 `rpm -qf --qf '%{NAME} %{VERSION} %{RELEASE}\n'`，并解析工具自身 `--version` 输出的上游版本号。
   - 任一工具不属于任何包、版本无法解析、`rpm` 的 VERSION 与工具自报版本不一致，或与认证身份的上游版本号（例如 22.1.8）不一致，就失败。包名、路径和 Release 只记录。
   - 检查的是绝对路径指向的实际文件，PATH 中另一个同名工具不影响结果。
4. **CMake 配置结果。** cmake 完成后，对生成的配置头求内容摘要：`include/llvm/Config/config.h`、`llvm-config.h`、`abi-breaking.h`、`Targets.def`、`AsmPrinters.def`、`AsmParsers.def`、`Disassemblers.def`、`TargetMCAs.def`、`tools/clang/include/clang/Config/config.h`。
   - 理由：spec 没有显式设置 zlib、zstd、libxml2、terminfo、libedit、libffi 等功能开关，LLVM 会按构建根里能否找到这些开发包自动开关，clang 的代码随之改变。这些结果不出现在 cmake 命令行里，而构建根包清单只记录、不强制，前三项全部通过时这类差异会被放过。
   - 配置结果还包括 CMake 编译参数探测（HandleLLVMOptions 中 `check_*_compiler_flag` 的结果）。这些结果直接加进每个编译单元的参数，既不在 cmake 命令行里，也不在配置头里。对 build.ninja 中 clang、lld、llvm-ar 及其依赖库各目标的 FLAGS，去掉构建目录前缀后求摘要，与配置头一并审计、一并启用。
   - 实施前，先逐行审计这些头文件和参数摘要：找出随构建根变化、但不影响 x86_64 代码生成的字段（例如 clang 的 HOST_LINK_VERSION），列入排除规则；同时确认清单是否完整。审计结果写成固定附件，冻结之后才启用。审计未完成，乙一不上线。

只记录、不强制（不一致时只在构建日志中打 warning）：

- 构建工具链的 Release 号与 VCS 提交号；
- 编译器、链接器、归档工具二进制的 SHA；
- 构建根完整包清单（rpm -qa 排序后）的摘要，以及其中 gcc、libstdc++、glibc 等头文件和库所在包的版本；
- 快照名；
- 上游源码包和各补丁文件的 SHA。

这样分的理由：基线是自托管构建，每次 QB 重建，下一次构建都会拿到新的编译器二进制，以及新的 Release 号和 VCS（71 号中 T 的 Release 为 2.1、D 为 5.1，VCS 随每个提交变化）。如果把这些设为强制，每发布一次就必须追加认证一次。

这一折中的保证范围有限，要写明：
- 上游版本号相同，只说明来源声明一致，不等于构建输入等价。
- 配置结果摘要能拦住构建根中功能开关的变化，但拦不住构建编译器或 libstdc++ 头文件本身的变化。
- BOLT 匹配门禁只检查 BOLT profile 的适配程度，不能替代 PGO、功能和消费者性能的认证；在"PGO 开、BOLT 关"的组合下，它完全不起作用。
- 快照漂移（构建编译器、libstdc++ 头文件等）会不会改变 clang 自身的代码，由下面的 T/D 归因实验给出证据。证据出来之前，这一折中只是临时安排，最终是否把工具链 Release 号或 libstdc++ 版本改为强制，由第 7 节裁决。

**T/D 两个身份与归因实验**：Toolchain（debug）和 Base-Dev（release）先作为两个不同的身份。同一份 BOLT profile 在 QB 上，Toolchain 的过期函数数 S=0，Base-Dev 为 S=23（71 号）。这说明两边送进 BOLT 的 clang 相对这份 profile 的匹配结果不同；它不给出两边全部代码差异的数量，也不给出原因。两边至少有三处同时不同：

- 调试参数：`-g2 -gdwarf-4 -g` 对无；
- 构建编译器：快照中的 clang 22.1.8-2.1 对 22.1.8-5.1；
- GCC/libstdc++：14.2.0-1.7 对 14.2.0-1.24。clang 自身大量模板是经 libstdc++ 头文件实例化的。

本包用 ThinLTO 构建。单独编译一个源文件只能得到 bitcode；去掉 -flto 得到的机器码又与最终链接不同。最终机器码是 lld 的 ThinLTO 后端在跨模块导入和内联之后生成的。所以逐源文件编译、比较 `.text` 的做法，即使得到"字节相同"，也可能只是没有复现 ThinLTO 链接，会把原因错归到快照。第一批的归因实验改为三步：

1. **描述差异（不重新构建）。** 在 D 的 rewrite 上加 `-report-stale`，取出失配函数名。这份名单只作调查入口，不当作全部二进制差异。在 T、D 各自送进 BOLT 的输入 ELF（带 relocation 的那一份）中，按符号取出这些函数的字节和大小，逐个比较，记录差异形态：只是地址相关的位移不同，还是指令序列、内联或寄存器分配不同；函数在一边被内联、合并或删除的单列。输入 ELF 取自本地完整构建（74 号），前提是该构建的最终产物与对应 QB 按口径 B 一致；不一致时这一步记为 UNKNOWN。这一步只回答"差异是什么"，不回答原因。
2. **析因构建。** 在 Toolchain 快照的构建根里，用 release 模式（D 的固定参数，无 -g）完整构建一次，做到 BOLT rewrite 为止。每次构建使用独立的 ThinLTO 缓存，记录实际工具和头文件所在包的身份。耗时约为一次完整构建（QB 上 Toolchain 约 2.6 小时、Base-Dev 约 1.6 小时），在第 2.4 节报备。
   - 判断依据不是 S。S 是 BOLT 的 CFG 哈希失配计数：S=0 不等于代码相同，两次都是 23 也可能是不同的函数集合。用第 1 步的方法，把这一格送进 BOLT 的输入 ELF 与 T、D 两边逐个比较全部函数（不只限失配名单），记录函数集合、缺失或合并的函数，以及结合重定位解释后的机器码差异。这一步不需要额外构建。
   - 这一格与 T 只差调试模式，与 D 只差快照。两组比较分别回答：在 Toolchain 快照上，调试模式是否改变代码；在 release 模式下，快照是否改变代码。第 7 节第 12 条需要的是后一个答案。
   - 只做三格时，只报告上面两个条件效应；两个因素之间是否有交互、总体归因如何，记为 UNKNOWN。需要回答交互时，再在 Base-Dev 快照里用 debug 模式补做第四格。不得仅凭 S=0、S≈23 或中间值判定"唯一原因"。
3. **定位到编译单元（需要时）。** 同时保留这些函数所在编译单元的原始预链接 bitcode 和它的 `llvm-dis` 原文，另外生成一份 `opt -strip-debug` 后的对照。比较文本时排除 ThinLTO summary 和模块哈希行，避免噪声。去掉调试信息后 IR 相同，不等于原始编译输入相同；预链接 IR 相同而最终代码不同，说明差异发生在 ThinLTO 链接阶段。结合导入的模块、ThinLTO 索引和后端命令定位；单个编译单元的规范化 IR 比较只用于定位，不能单独证明差异来源。

保存 `-report-stale` 原文、每次构建与编译的完整 argv、缓存条件和函数级字节的 SHA，结论写进清单的身份说明，并注明只覆盖被测的身份。完成不了的对照记为 UNKNOWN。一次对照实验"没有观察到快照影响"，不能推广为以后任意同版本快照都安全，也不能据此让新快照自动继承认证。归因之前按保守做法处理：profile 在 Toolchain 配置下生成；Base-Dev 通过追加认证后，写进同一份清单；认证不通过，就为 Base-Dev 单独生成一对 profile。

**检查时机**：

- %prep：检查编译输入摘要、各 profile 的 SHA；
- cmake 完成后、ninja 之前：检查实际参数、cmake 命令行、配置结果摘要和工具链版本号；按开关组合检查 PGO 的生效情况（见下）。不依赖事后扫描构建日志；
- BOLT 之前：记录实际输入 ELF 的身份。

PGO 生效检查按开关执行：PGO 开启时，检查预期作用范围内的目标在 build.ninja 中确实带 `-fprofile-instr-use=`，并且路径指向认证映射指定的那个文件（核对 SHA）；PGO 关闭时，检查这些目标没有意外带上 profile-use 参数，也不要求提供 PGO 资产。BOLT 的资产检查按组合单独执行，两者互不影响。

身份不符时，打印有差异的字段并停止。

**spec 中的使用**

- 新增 Source：PGO profile、与之成对的 BOLT profile、清单。现有的 Source1200（非 PGO 用 BOLT profile）继续保留。
- 当前输入身份必须出现在清单的认证列表中，否则构建失败。清单可以记录多个已认证的身份。
- 通过 LLVM 自带的 CMake 选项 LLVM_PROFDATA_FILE 传入 PGO profile。上游 CMake 在文件不存在时只打 warning，所以 spec 在 cmake 之前自己检查文件存在，cmake 之后检查 build.ninja（见上文"检查时机"）。
- **PGO 匹配程度**：
  - 先确认 profile 的类型：Frontend、IR 还是 CSIR，并核对对应的使用阶段。LLVM 的插桩构建默认生成 IR profile，匹配在 IR PGO pass 中进行；前端的 -Wprofile-instr-out-of-date 汇总诊断不适用于 IR profile，而 IR 侧的缺失与 COMDAT/weak 不匹配警告默认被抑制（llvm-22.1.8 的 CodeGenModule.cpp 第 857–872 行、PGOInstrumentation.cpp 第 1407–1439 行）。
  - 只有取得同一统计域内完整的 matched、missing、mismatched 计数，才计算匹配率，并写明统计单位（函数实例还是去重函数），以及 COMDAT、重复编译单元和 ThinLTO 阶段如何处理。
  - 不得用警告条数或 profdata 记录数代替当前构建的分母。取不到完整计数时，记为 UNKNOWN；不把"没有警告"解释为"零过期"，也不据此追加认证身份。
  - 辅助指标：本包用 ThinLTO，IR PGO 的注解在预链接阶段完成，构建树中 clang 各编译单元的 .o 就是带注解的 bitcode。对这些 bitcode 执行 `llvm-dis`，统计已定义函数中带 `function_entry_count` 元数据的比例，称为"最终 IR 注解覆盖率"，不得称为 PGO 匹配率：最终预链接 bitcode 中的函数集合不一定就是 profile-use 当时的候选集合（之后还有删除、克隆和内联），不同编译单元的同名局部函数也不是同一个函数，同名 ODR 定义也可能有不同的 CFG/profile hash。
  - 完整的匹配计数，优先在 profile-use 查询发生的阶段取得：记录模块身份、函数/profile key、函数 hash 和 matched/missing/mismatched 状态。局部函数按模块区分；COMDAT/ODR 去重必须保留 hash 不同的定义。统计范围覆盖实际链接进 clang 的 LLVM/Clang 编译单元。只能取得最终 IR 元数据时，匹配率继续记为 UNKNOWN。
  - 如果 profile 是 CSIR，上下文敏感的那部分在 ThinLTO 后链接阶段才使用，预链接 bitcode 的统计覆盖不到，要单独说明。
  - 需要额外诊断选项（如 `-mllvm -pgo-warn-missing-function`）时，只在离线认证构建中使用。这类选项会进入静态库成员的记录命令，而转换器会拒绝 `-mllvm`，所以认证构建要关闭转换，或另行处理。
  - llvm-profdata 统计的有 profile 函数数与计数占比，作为辅助记录，和上一个已认证基线比较，不作分母。
  - 发布构建中，这些指标只记录在构建日志末尾，不拦截。
  - 计数方法本身先用夹具验证：全匹配、完全缺失、部分 hash 不匹配、仅 COMDAT 不匹配、同一函数跨编译单元重复、执行次数为 0 的函数、健康编译单元不产生警告、跨编译单元的同名局部函数、同名 ODR 定义 hash 不同、匹配后被删除的函数、克隆出的函数。报告的比例必须与已知真值一致。
- **追加认证**：输入变化后，离线完成兼容性认证，才能把新身份追加进清单，否则就重新生成。认证内容：
  - PGO 确实生效（build.ninja 检查）；
  - PGO 匹配率（计数方法验证通过后才可用；数值阈值在基线实验后另行裁决，不沿用 BOLT 的 5%）；
  - BOLT 匹配门禁通过；
  - 第 2.5 节身份一致性矩阵的冻结子集，以及发货库消费者验收；
  - 冻结留出集（第 3.1 节第二层）上的快速性能检查：与已认证的 PGO 版本比较，不与非 PGO 版本比较（PGO 静默失效时，clang 只是退回非 PGO 水平，和非 PGO 版本比照样"没有回退"）。判据为配对几何均值比值不劣于事先写定的阈值，阈值在第一次追加认证之前写定。
  
  PGO 匹配率为 UNKNOWN 时，不得据此通过追加认证；PGO 诊断计数只是认证的附件，不能单独作为认证依据。
- BOLT 侧继续沿用 -stale-threshold=5，以及 helper 的 R、S/N 都不超过 5% 的硬门禁，不放宽。
- **开关组合与 profile 选择**：PGO 和 BOLT 分别有 %bcond 开关。BOLT 默认开启；PGO 在第二批默认开启的条件见第 6 节。

  | PGO | BOLT | 使用的 profile |
  |---|---|---|
  | 关 | 关 | 不用 profile，普通基线 |
  | 关 | 开 | 现有的 Source1200（非 PGO 用 BOLT profile），行为与当前基线完全相同 |
  | 开 | 关 | 清单中按当前身份（T 或 D）认证的 PGO profile |
  | 开 | 开 | 该 PGO profile，以及按当前身份认证的成对 BOLT profile |

  - 按"（T/D 身份，PGO 开关，BOLT 开关）"在清单中查找唯一的资产映射，不限定资产总数。T、D 可以引用同一对 profile，也可以引用不同的配对资产。使用任何 profile 之前，先检查映射和 SHA；匹配门禁只判断适配程度，不承担识别"是否拿错资产"的职责。
  - 现有的 Source1200 已同时用于两边：T 的 S=0，D 的 S=23、R=0.10%，都在 5% 门槛内。PGO 的配对资产按同样的方式认证，并记录两边各自的匹配数据。
  - 关闭 PGO 时，行为与当前基线完全相同（包括总部转换器的改动），不回退到旧的源码链。
  - 训练或匹配失败时明确报错，不在构建中静默降级；需要回退时，靠提交修改开关实现。

**PGO 的作用范围**：LLVM_PROFDATA_FILE 加在整个 CMake 构建的全局编译参数上，不是只给 clang 用的。实施前，必须先从构建日志中盘点所有带 -fprofile-instr-use 的编译单元及其所属目标，并公开清单。处理规则：

- **主构建中的 LLVM/Clang/LLD 库和工具：** 允许在作用范围内，属于预期行为。lld、llvm-ar 不单独训练，但它们的代码同样会变，要按第 2.5 节验收。
- **compiler-rt、libomp 等随包发布、会被其他包链接的运行库：** 本期排除在 PGO 作用范围之外。若盘点发现它们已在范围内，先用 CMake 隔离；隔离不了的，列为裁决项，并补充 ABI、功能和下游运行性能/内存验收。
- **静态库转换器：** 成员的 recorded command 会多出 -fprofile-instr-use 等参数。转换器必须给它们明确分类：分支权重和入口计数已写在 IR 中，因此不重放。不能笼统忽略所有 profile 参数，未知参数照旧拒绝。这项改动要用真实的 PGO bitcode 成员做转换验证，并验证 GNU ld 与 lld 两类 static-devel 消费者。该参数带构建根的绝对路径，会进入成员的 .GCC.command.line；PGO 开、关两组产物在这一节上必然不同，这是 PGO 本身带来的变化。另有一条维护约束：转换器把 -g0 也算作调试选项（以 -g 开头），release 声明下带 -g0 的成员会被拒绝。当前 7706 条命令中 -g0 出现 0 次；将来配方若引入 -g0，要先把判定改为"实际产生调试信息的选项"，再重新认证。
- **llvm-static-devel 和共享库：** 归档成员和 libLLVM.so、libclang-cpp.so 等发货库的代码，都会随 PGO 变化。这一点单独列在变更说明里，并按第 2.5 节对这些库的消费者做验收。

**-use-old-text 放不下时的处理**（缺口 686,688 B，占可用 .text 的 0.85%）

- 现有参数已经包含 -split-functions、-split-all-cold、-split-eh，这些不是还能新加的手段。
- 候选手段，合成一个实验批次一起测，因为它们会互相影响基线：
  1. 允许改用新段（现状行为）。记录"需要 / 可用"、最终 strip / RUNPATH / debuglink 处理后的文件大小、LOAD 映射和运行时 RSS。参考数据：非 PGO 口径下，用旧段的版本为 152,532,296 B，不用旧段的为 183,224,160 B；以用旧段为基准，不用旧段大约 20.12%（37 号第 10 节记录的 16.75% 是反方向、以不用旧段为分母算出的缩小比例）；PGO 口径还没有打包后的数字，本月先补这一项。

- 不论走哪条路径，产物都必须通过与旧段路径相同的全部正确性、安全属性、符号化和打包门禁，不能只凭退出码 0 判定可以发布。新增或变化的 BOLT 警告必须归因。
- 每组都记录 strip 后大小与 R、S/N。数据齐了再裁决（第 7 节）。在此之前，暂按"允许新段，同时打印数据"运行，不让构建失败。

### 2.5 正确性验收

**编译器身份一致性**：同一源码、配方、工具链、resource-dir 和 sysroot 下，比较 PGO 开/关 × BOLT 开/关四种组合。比较三项：目标文件字节、退出码、stderr 原文，要求全部相同。

输入分四类，在验收前冻结清单：

1. 现有 90 份 LLVM C++ 输入（20 个源文件 × 3 个目标，60 个唯一内容 SHA；67 号已恢复）。
2. 新增至少 30 份真实 Tizen 包的 C 预处理输入，其中多数小于 1 MB，覆盖三个目标。
3. 从一次真实构建的静态库转换中，冻结 100 个 bitcode 成员及其内容 SHA。对同一份输入，四个 clang 执行同一版转换器生成的完整后端参数，保持路径、resource-dir 和输出文件名一致；不直接重放原始的前端命令。样本要覆盖带 PGO 元数据的成员、无函数属性的成员、含 module asm 的成员，以及与原生成员混合的归档。这条路径的产物会进入 llvm-static-devel。
4. 多种优化等级和语言标准的小样本（-O0/-O1/-O2/-Os/-O3，c11/c++17/c++20），未预处理的源码输入（覆盖预处理与头文件搜索），汇编输入，以及 PCH、模块和 ThinLTO 编译—链接路径。

四种组合在 Toolchain（debug）和 Base-Dev（release）两种编译器构建模式下各执行一遍完整矩阵。下游输入同时覆盖不带调试选项和带 -g/-gdwarf-4 的情况：被编译的对象该不该有调试节，由这个用例自身的编译参数决定，与 clang 自身是 T 还是 D 模式无关。release 模式的 clang 同样要验收"用 -g 编译用户程序时，生成并保留正确的调试信息"，包括 C/C++、PCH/模块和静态库消费者，检查对象的 DWARF 内容和调试器定位，不只看调试节是否存在。所有比较使用相同的驱动路径，避免路径差异污染 stderr。

**链接路径**：

- 用一个真实 C/C++ 包，在四种组合下各完成一次编译加链接，比较最终 ELF，默认逐字节相同。记录节或 build-id 若有差异，必须逐项归因，说明差异来源及依赖关系，不能按节名直接忽略。内容相同时 build-id 也应相同，所以 build-id 不作为例外。
- lld、llvm-ar 在 PGO 作用范围内，因此用固定输入分别验收 lld 的链接输出和 llvm-ar 的归档输出。

**发货库的变化**：PGO 会改变发货的 LLVM/Clang/LLD 库，以及 llvm-static-devel 的成员。四个 clang 对固定输入的输出相同，不能代替这一项验收。

- 从仓库依赖中列出链接 libLLVM.so、libclang-cpp.so 或 llvm-static-devel 的 Tizen 包。
- 检查 ABI。
- 验证静态和共享两类消费者的功能。
- 对代表性消费者测量运行性能和内存（三类内存中的第三类，不得回归）。

**原则**：

- "PGO/BOLT 不改变编译器输出"是待验证的要求，不是前提。任何不一致都按缺陷处理，先阻断，再定位到具体的优化或改写，不能以"差异很小"放行。
- 这项检查是很强的筛选，但不代表覆盖所有编译路径。

**先验证方法本身**：这套验收至今没有完整跑过（63 号 0/90，67 号恢复输入后也没有重跑）。第一批先用现有的两个版本跑通一次：

- V1b：基线以 --without clang_bolt 构建；
- V2：基线本身。

方法可用之后，再用于 PGO 版本。

**BOLT 改写警告专项**：解释两处"jump past end → nop"警告：

- 被换成 nop 的跳转是否可达；
- 它们落在函数的哪一部分；
- 现状发货的非 PGO BOLT 日志里是否也有同样的警告。

另外，针对这两个函数补定向输入（aarch64 上的分支密集代码、x86_64 上能触发 LEA 三地址转换的代码），比较 BOLT 前后的输出。1551 条 relocation 分析警告也要归因。

**可复现性**：

- 用同一份清单、在两个独立的干净构建根中构建，比较最终 ELF 和 RPM payload，按口径 A 判定。
- 离线生成本身不承诺可复现：profile 一旦固定，就以 SHA 钉住。但要记录两次生成之间的差异，作为维护参考。

**其余验收**：

- 本地 T/D 两个配置完整构建；
- install/LLDB 21 项检查；
- 安全属性、debuglink 与符号化检查；
- accel 实物验证；
- 混合链接的安装后 CMake 消费者：用安装后的 CMake exports 分别构建一个默认（共享）消费者和一个显式选择静态组件的消费者，确认 generator expression 在构建树之外的行为与预期一致。现有的 NEEDED 断言和手写链接消费者不能完全代替这一项；
- QB 两个项目全部架构通过。

## 3. 测速方法

### 3.1 本地（只给方向，不作结论）

**测速集**：采集 profile 前，冻结训练集与测速集。隔离同时按内容 SHA 和原始源文件检查；同一源文件的不同目标、参数或预处理版本归为同一组，不能分散在训练和测速两侧。

已核实的现状：

- 现有 BOLT 训练集与 90 份测速输入的内容 SHA 交集为 0。
- 但源文件交集是 10 个：BOLT 训练用的 10 个 LLVM 源文件全部在测速集里。

因此测速集分三层，分别报告，不合并成一个总比值：

| 层 | 内容 | 用途 |
|---|---|---|
| 第一层 | 训练过的 10 个源文件 × 3 个目标（30 条） | 只用来观察 profile 是否生效，不作为速度结论 |
| 第二层 | 未训练的另外 10 个 LLVM 源文件 × 3 个目标（30 条） | 同项目留出集 |
| 第三层 | 新采集的真实 Tizen 包预处理输入，至少 30 条，C 与 C++ 各半，分布在三个目标上 | 用于判断"平台包编译是否变快" |

- 第二、三层与 PGO、BOLT 两份训练集在源文件层面也必须不相交。
- 重复内容只保留一份参与计权，统计时按源文件分组处理相关性。
- 三层清单、来源包名、SHA，以及与训练集的交集表，作为测速报告的固定附件，每次测速都重新生成。

**启动开销**：空 C 文件和空 C++ 文件，各执行 -fsyntax-only 1,000 次，记录 wall 和 user+sys 总和。BOLT 版 clang 比普通版大 9.0%，若退回新段会更大，所以启动与映射开销必须单独量化，否则在大 TU 上看不出来。这一项也用于给第 5 节的几项排序。

- 连续执行的结果标为"热缓存启动"。
- 冷启动另列：每次运行前丢弃页缓存，需要提权时按既有弹窗方式进行；做不到时标为 UNKNOWN，不由热缓存结果推断。

**版本**：V1b–V4 都从同一认证基线构建，只改变开关：

| 版本 | 内容 |
|---|---|
| V0 | tizen_base 当前 HEAD 的 GCC 编译版（f999bd40 的 QB 产物）。作为总部现状的产品参考单列，不用于分离 PGO/BOLT 的因果收益 |
| V1a | 基线，关闭 BOLT，关闭混合链接（全部动态链接）。只用于解释 V1b 与 V0 之间"混合链接"那一部分 |
| V1b | 基线，关闭 BOLT |
| V2 | 基线 |
| V3 | 基线 + PGO，关闭 BOLT |
| V4 | 基线 + PGO + BOLT |

报告：

- V1b/V1a（混合链接）；
- V2/V1b（BOLT）；
- V3/V1b（PGO）；
- V4/V3（在 PGO 上叠加 BOLT）；
- V4/V2（在当前 BOLT 方案上增加 PGO 的直接收益）；
- V4/V0（相对总部现状的总收益）。

**主结论的对象**：qemu-accel 取用 Toolchain 项目的 llvm（已确认，第 7 节第 17 条）。以 Toolchain（T）的发货二进制作为测速的主结论；Base-Dev（D）的结果作为补充报告，不与主结论合并。

**二进制形态**：一律使用各模式真实 RPM payload 中的最终二进制，不使用构建树中的中间产物。T 使用带 debuglink、配有符号文件的发货形态；D 使用不带符号文件和 debuglink 的发货形态。不人为统一两种模式的调试布局。每个版本记录所用二进制的路径、大小和 SHA，并与 RPM payload 核对。

**执行**：

- 每轮的版本顺序，用测量前固定种子的平衡随机顺序，或轮换起点，避免某个版本长期排在固定位置。
- 加入同一编译器的 A/A 对照。
- 每个版本的首轮作为预热，弃用。
- 每份 TU 在固定 CPU 上串行编译，用 /usr/bin/time -v 记录 user+sys、wall 和最大 RSS。
- CPU 频率：测量前记录调频策略（scaling_governor）、睿频开关和实际频率范围，测量期间每轮记录一次。能固定时固定为同一策略并关闭睿频；不能固定（需要提权而无法取得）时如实记录，并在报告中注明。要分辨 3% 的差异，频率状态不能不控制。
- 每轮开始前记录 load average。超过 1 时最多等待 10 分钟，仍然超过的，把该轮标记为"有干扰"并从统计中剔除，剔除的轮次单独列出。剔除规则在测量前固定，不根据快慢事后删除。
- 轮数：
  - 先做独立的 pilot，用配对的 log 时间差估计波动。
  - 在正式测量前写定三件事：正式轮数的计算方法（目标为分辨 3% 差异、双侧 95%、power 0.8）、最大轮数，以及达不到精度时的处理。
  - pilot 不计入正式的置信区间；正式测量中不根据中途结果增减轮数。

**统计**：

- 主指标为冻结负载上逐 TU 配对比值的几何均值，不用"每轮总和的中位数"。
- 区间估计同时保留两层相关性：源文件是跨目标、跨参数的共同分组，测量轮是时间块。
- 区间描述的是这份冻结负载，不能直接外推为"所有 Tizen 包"。
- 统计脚本先用合成数据验证：已知零差异、已知 3% 差异、带轮次共同漂移三种情况，并确认重复的源文件不会增加独立样本数。
- user+sys 和 wall 都报告。
- 方向判断依据预注册的配对 log 比值估计及其置信区间，并要求 A/A 通过预先规定的稳定性检查。不要求每一轮都同方向（真实的小收益下，个别轮次反向是正常的），但要报告反向轮次和轮间异质性。区间跨越零收益，或 A/A、精度要求没有满足时，报告"数据不足以分辨"，这是合法结论。预注册的主比较与探索性结果分开报告。合成数据验证中加入"总体改善 3%、部分轮次反向"的案例。
- 同时报告三类内存中的第二类（编译时的最大 RSS）。

**包体积**：clang 所属 RPM、它的符号包、实际的 accel 包，各自的压缩大小、安装大小和文件数量；llvm 主包只作补充。

| RPM 压缩方式 | — | 时长 | RPM 文件字节变化 | 裁决项，默认不做 |

**本期不做的：**

- 转换成员去重。转换参数含 -frecord-gcc-switches，输出路径会写进 .GCC.command.line，复用的产物无法与现行输出逐字节相同。要做的话，必须先定义缓存键（输入内容、完整后端参数、工具身份、路径上下文），并把记录节的归一化作为效果变化单独裁决。
- 改变转换的中端流程。会改变代码生成，不属于"效果不变"的优化。
- 静态库不走 ThinLTO、直接编成原生对象。这样要从源码再编译一遍这 3,853 个成员（前端加中端），开销大于现在从 bitcode 转换；归档内容也会改变。评估后不采用。
- 压缩调试节、split DWARF、改用 DWARF 5、降低 -O 等级、减少调试信息。都会改变产物或效果。

### 4.3 验收

- 每个候选单独成一个提交，各自给出时长、三种口径的内存、磁盘曲线，对比同快照、同口径的基线。
- 每个候选都按口径 A 比较全部 RPM payload，允许的差异只限第 0.3 节口径 A 的例外。
- 改动 debuginfo 或 debuglink 输入的候选（find-debuginfo 并发度、中间产物清理、BOLT 重链复用），是口径 A 的直接用例。不能因为"改了之后和 QB 更像了"就判通过。

## 5. 其他提速方案评估

下表是探索顺序，不是已测收益的排名。先确认热点和适用条件，再决定是否实现；没有本项目证据的收益一律记为"待实测"。启动开销基准（第 3.1 节）在原型之前先做，作为排序依据。

| 方案 | 原理 | 前提与风险 | 本月目标 |
|---|---|---|---|
| 链接期相同代码折叠（-Wl,--icf=safe） | LLVM 模板实例化多，代码相同的函数可以折叠，.text 变小 | 不用 =all，它会破坏"不同函数地址必须可区分"的假设。会改变普通 clang，属于改变编译器产物的优化，要重新绑定相关的 profile 身份。与 -use-old-text、BOLT 重链复用、大页合成一个实验批次。不保证能缓解旧段容量缺口，因为旧段可用量和 BOLT 需求量可能同时缩小 | 本地原型：同时记录旧段可用量与 BOLT 需求量，不能只看普通 .text 变小；三层 TU 的时间与 RSS；四种组合的身份一致性；函数地址可区分性抽查 |
| clang 驱动与 cc1 同进程 | 每次编译只映射一次 clang | LLVM 10 起默认在进程内运行 cc1（CLANG_SPAWN_CC1 默认 OFF），预计已经生效。先读构建根 CMakeCache，并用 strace -f -e trace=execve 核实；已生效则关闭此项 | 只做核实 |
| 替换内存分配器（在 clang、lld、llvm-ar 的链接中静态链入 mimalloc 等） | 编译器有大量小对象分配 | 依赖性质是构建期依赖（开发包与静态库），不是运行期 Base 包。先审计 LLVM 22.1.8 已有的分配器入口（如 LLVM_ENABLE_RPMALLOC 及其平台限制），用最小的 configure/link 探针确认它在 Tizen x86_64 上是否可用、作用于哪些目标；确认不可用或范围不合适，再设计只作用于三个驱动的 mimalloc 等接入。不把"存在 CMake 选项"等同于可以部署。原型之前，先确认 Tizen 是否有对应包、glibc 兼容性和许可（mimalloc 为 MIT）。可能提高第二类内存；分配地址变化可能触发"指针顺序影响输出"的问题，必须做身份一致性验收 | 先做可用性与合规检查，通过后再做本地原型 |
| 代码段大页（BOLT -hugify） | 降低 clang 大代码段的地址转换开销 | 高风险，不进入默认发货配置。LLVM 22.1.8 的 hugify runtime 在系统调用失败时会调用 reportError 并退出进程（bolt/runtime/hugify.cpp、common.h），不满足页缓存 THP 条件时还可能重新映射热代码，不能假定失败会自动降级；一旦出错，就是 clang 启动失败，违反"不能导致其他包编译失败"的硬约束。0x200000 对齐还会加重 -use-old-text 的容量缺口。没有 iTLB 计数之前，不预设收益 | 只做隔离环境原型：先审计实际 runtime 和构建机内核的限制，再验证 THP 不可见或禁用、madvise 被拒、内存不足、mmap/mprotect 失败、多个 clang 并发等情况。任何启动失败都不能放行。不得通过修改共享构建机的全局 THP 配置来证明可以部署 |
| perf 采样驱动优化（AutoFDO/Propeller） | 用真实负载上的采样 profile | 需要硬件 LBR 和权限；QB 上不能采样，不等于不能离线采集，但要证明离线负载与部署条件相符。收益待测 | 只做可行性调研，列入后续计划 |
| 静态 clang 的全程序去虚拟化 | 减少虚调用 | 可能破坏 clang 插件接口，正确性风险较高 | 只做可行性调研 |
| -fno-plt、-Bsymbolic-functions 等动态链接优化 | 减少 PLT/GOT 与符号抢占开销 | 对本设计的价值路径收益很小，因为 qemu-accel 取出的 clang、lld、llvm-ar 已是静态链接。但其余二十多个工具，以及 libLLVM.so、libclang-cpp.so 的使用者，仍然走共享库；-Bsymbolic 还涉及符号抢占语义和插件兼容性。以后优化那些工具时需要重新评估 | 不做，记录理由与适用边界 |
| 提高 -march 等级 | 使用更新的指令集 | QB 构建机 CPU 未知，可能 SIGILL；与"沿用项目 -march"的裁决冲突 | 不做 |
| 平台包默认使用 lld | 缩短包的链接时间 | 在单独的工作线中跟进 | 不在本设计内 |

## 7. 需要裁决的事项

1. **BOLT profile 的交付方式：** 推荐乙一，即两份 profile 都预采集、离线成对生成。备选是乙二（BOLT 改为构建内采集），实测代价为 +461 s、单进程峰值 VmHWM 17.0e9 B、临时磁盘 +3.8 GB，还要重新认证任务白名单和 profile 门禁，并把训练输入作为源文件发布。

5. **身份一致性验收失败时：** 推荐一律按缺陷处理，定位原因之前不放行。
6. **PGO 作用范围：** 运行库本期排除在外；llvm-static-devel 成员随 PGO 变化，是否接受。PGO 默认开启之前必须完成这一条。
7. **第二类内存**（编译其他包时编译器的内存）可接受的变化幅度与报备标准。
8. **llvm 源码包和 debugsource 包与 QB 的剩余差异**（17 个文件的权限 0664 对 0644、QB 写入 spec 的 VCS/Release/%patch 写法、debugsource 的 Release 路径前缀）：是定义为限定范围的已知环境差异单列显示，还是继续判 FAIL。

## 8. 风险

- **基线依赖两个尚未合入的总部 change：** 359934（patch set 10，NEW）和 357163（NEW），tizen_base HEAD 仍是 `f999bd40`（回退为 GCC 编译）。任何一个改版或不合入，三个提交都要重新改接；V0 与 V1b–V4 之间"用 clang 编译 LLVM 加 ThinLTO"这一差异的归属也会变。
- **ARM 包并非完全不变：** 混合链接提交修改的 CMake 模块会安装进所有架构的 llvm-devel 和 clang 包。ARM 上构建行为不变，但载荷文本会变；已裁决作为已知例外接受（第 7 节第 15 条）。77 号已完成 ARM 包与改动前基线（PS7）的逐包比较，差异只有这两个模块文件；以后的 tree 只要 ARM 载荷与 1225393/1225395 相同，就沿用这一结论，出现其他差异须停止归因。
- **第五轮修复改变 tree：** 修复只涉及门禁、取消状态、重定位与 ar 解析检查、日志和提交说明，但仍需 QB 重跑和本地完整构建；转换器的重定位类型改为显式宽度表、未知类型直接失败，Toolchain 构建中带调试信息的成员会经过新检查，所以修复前要先在带调试节重定位的真实成员上验证（78 号）。
- **BOLT 的 nop 改写还没有解释：** 两处"jump past end → nop"分别位于 AArch64 和 x86_64 后端的函数中，另有 1551 条 relocation 分析失败。本月必须给出解释并补定向验证（第 2.5 节）。
- **PGO profile 可能不完整：** 插桩构建时有 830 条计数器耗尽警告，这些数据是否进入了发布 profile 还不清楚（UNKNOWN）。如果进入了，间接调用的 value profiling 不完整，可能削弱 PGO 收益。
- **身份检查放过漂移：** 只记录、不强制的输入（工具链 Release/VCS、编译器二进制、构建根头文件和库）发生变化时，profile 可能逐渐失配。配置结果摘要能拦住构建根功能开关的变化，但拦不住构建编译器和头文件本身的变化。BOLT 匹配门禁只能发现 BOLT profile 的大幅失配；PGO 的失配和收益下降，它看不到。在"PGO 开、BOLT 关"的组合下，只能靠追加认证、发布日志中的记录和定期测速发现。T/D 的 S=23 已经说明两套构建输入存在实际差异，原因待归因。
- **速度收益可能比预期小：** 目前只有噪声很大、而且是在训练集上测的本地数据。分层测速后，平台包那一层的收益可能明显小于 LLVM 源码那一层。最终以 QB 数据为准。
- **profile 随源码发布可能被质疑：** 52.5 MB 的 PGO profile 加上两份 BOLT profile 放进源码包，总部可能有顾虑。备选是甲，代价是新增步骤约 81 分钟（规划值），磁盘规划下界 122–126 GiB。
- **"理论上不改变产物"的项可能证不出来：** 并行度调整、BOLT 重链复用，理论上不改变发布产物，但必须逐字节实证，实证不通过就放弃该项。相同代码折叠会改变编译器产物，不属于这一类，按第 2.5 节验收。
- **QB 构建机的内存和磁盘上限未知：** 每项改动都只报实测值，不作"可以接受"的判断。
